# Makefile with the development tasks

Date: 2026-09-02 20h35

## Request

Add a `Makefile` at the repository root with four tasks: `install`, `build`,
`test` and `up`.

## Why

The commands are already written down in [docs/development.md](../docs/development.md)
and in `.github/workflows/build.yml`, but spread across three places and with an
ordering that is not obvious from reading them: the wasm is a **build input** to
the Vite project, so `wasm-pack build` has to run before anything under `web/`.
Someone who clones the repository and runs `npm run dev` gets a broken page and
no explanation.

The Makefile is the shortest way to encode that order once. It does not become a
new source of truth: every recipe is the same command CI runs, and the version
of Rust still comes from `rust-toolchain.toml` and nowhere else.

## Planned tasks

| Task | What it does |
| --- | --- |
| `make install` | Rust toolchain from `rust-toolchain.toml`, `wasm-pack` if missing, the test corpus, and `npm ci` in `web/` |
| `make build` | wasm, release CLI, static site in `web/dist` |
| `make test` | `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test`, the wasm smoke test, `oxlint` |
| `make up` | wasm if stale, then the Vite dev server |

Details settled while writing it:

- The `wasm-pack build` line is copied verbatim from `build.yml`, flags
  included. CI diffs `web/pkg/vektro.d.ts` against what it compiles, so a local
  build made with different flags would produce a spurious failure there.
- `web/pkg/vektro_bg.wasm` and `web/node_modules` are real file targets with
  prerequisites, so `make up` twice in a row does not recompile the wasm. The
  wasm depends on every `.rs` under `src/` plus `Cargo.toml` / `Cargo.lock`.
- `make test` runs the debug suite only. CI also runs `cargo test --release`
  because release turns off overflow checks; locally that means a second full
  release build, and the target is meant to be run often. Noted in the help text.
- `wasm-pack` is installed with `cargo install --locked` when absent, rather
  than assumed. `npm ci` and not `npm install`, matching CI and the lockfile.
- `scripts/corpus.sh` already no-ops when the corpus is present and verified, so
  `make install` can call it unconditionally.

## Walkthrough

- `Makefile` (new) — the four tasks, plus `help` as the default goal and two
  file targets (`web/pkg/vektro_bg.wasm`, `web/node_modules`) that carry the
  ordering and keep repeated runs cheap.
- `docs/development.md` — a "The short way" section ahead of the existing
  command listings, saying what each task does and that none of it is a new
  source of truth.

Verified on this machine:

- `make help` prints the four lines; `make -n build` shows wasm -> CLI -> site.
- `make test` builds the wasm, runs `npm ci`, passes `cargo fmt --check`, and
  then **fails on clippy** — see below.
- The rest of the `test` recipe passes when run by hand: 20/20 suites green,
  `scripts/web-smoke.mjs` all ok, `oxlint` exits 0 (five unused-variable
  warnings, none of them errors).
- `make build` produced `target/release/vektro` and `web/dist` (322 KB wasm,
  119 KB js), reusing the wasm from the previous run instead of recompiling it.
- `make up` served the page; Vite came up and answered.
- `web/pkg/vektro.d.ts` is byte-identical after the local `wasm-pack build`, so
  the flags copied from `build.yml` are the right ones and CI's diff step stays
  quiet.

### Found while testing: clippy is already red on this branch

`cargo clippy --all-targets -- -D warnings` fails at `src/lib.rs:88`
(`derivable_impls`): `impl Default for Config` sets every field to its type's
own default, so clippy wants `#[derive(Default)]`.

It is not from this change and not from the working tree either — the same code
is in `HEAD` (`ca278ad`), so the branch is already failing that CI step. Left
alone: it belongs to the découpage work in flight, and adding a derive to a
public type is not a Makefile's business.

## Extension 2026-09-02 21h05 — fixing `make test`

`make test` was failing on the pre-existing clippy error described above, so the
target did not do its job. Fixed by taking clippy's suggestion: `Config` gets
`#[derive(Default)]` and the hand-written `impl Default for Config` goes away.

Behaviour is unchanged — the manual implementation set every field to exactly
its own type's default (`Segmentation::default()`, `Fit::default()`, `None`,
`false`), which is what the derive produces. `Segmentation` keeps its manual
`impl Default` because it is an enum picking `Grid`, which no derive can express
without an attribute.
